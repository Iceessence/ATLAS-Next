# Roadmap

## Decision after independent NEXT-004 review

| Option | First useful outcome | Dependency and measure |
| --- | --- | --- |
| A. Local conversation and coding assistance | An owner selects a project source file, asks where a symbol is defined and follows up about its parameters. Both answers cite the correct file revision and lines. | Read-only and offline. Compare verified task completions, wrong answers and time against ordinary local search. Exercise two unfamiliar projects, scope changes and ambiguous names. |
| B. Authorized internet and document research | Resolve one owner question from approved sources, preserve citations and revisit a stale or conflicting claim. | Begin with selected local documents. Network access requires an isolated fetch boundary and explicit destinations, privacy and resource limits. Score source support, safe withholding and later reuse. |
| C. Independently evaluable native training | Refit one existing specialist for a recurring measured failure, then accept or reject it on unfamiliar work. | Accumulate eligible outcomes from A. Freeze the baseline and evaluation protocol first. Custodian controls private expectations and promotion. Compare quality, calibration, cost and reference assistance. |
| D. Isolated execution for self-development | Reproduce one authorized source change from input revision through disposable build, independent check and rollback. | Requires independently verified guest configuration, revocation, budgets and safe output handling. Host execution stays disabled until the boundary is qualified. |

Proposed first slice is A, with C’s independent scoring agreed before implementation. It gives the owner a useful local interaction and supplies outcomes for the next specialist comparison. B can start with document organization and verification alongside that work. An online research pilot follows verification of its isolated network boundary. D gates running proposed changes and later self-development. The next assignment belongs in the reciprocal handoff after Hydrogen’s verdict.

Research should preserve exact file or URL, retrieval date, version, digest, passage and scope for each claim. Keep raw, provisional, verified, contradicted and rejected states distinct. Recheck time-sensitive evidence before reuse and retain conflicting revisions. Treat retrieved instructions as data. Isolate approved network activity from personal accounts, identity, payment methods and host files. Only independently supported claims and successful procedures enter authoritative reuse.

## Dependencies retained from the original roadmap

1. Independent reviewer reruns the exact candidate, checks package/runtime closure, OS behavior, task integrity and corpus labels, and issues a verdict. Keep the native binding in shadow mode.
2. Collect consented public tasks from real distinct projects. Separate source families, authoring templates and downstream scoring. Provision evaluator-owned storage/account inaccessible to training and model tuning. Preregister a strong baseline, outcome evidence, costs and a fresh confirmation set. Archive rejected experiments with provenance and failures.
3. Expand to authorized local file import, scoped access and stronger retrieval with exact citations. Add durable resource-managed background work, checkpoint continuity and safe rollback only where exercised by a real workflow.
4. Prepare a separately licensed, disposable Windows guest with owner-approved administrative setup. A reviewer must inspect actual no-NIC/no-redirection/no-personal-volume configuration, resource caps and guest reset, then test synthetic canaries, explicit revocation and quarantine-only outputs. Current account cannot inspect the candidate guest. No physical-host fallback.
5. Compare separate Engineering and Research decisions on verified software/evidence tasks. Use outcome and cost measurements before allocating additional model capacity, deploying workers or starting an application evolution experiment.
6. Build project-aware coding and creative assistance from authorized project versions, conventions, file spans and verified outcomes. Validate copy-ready changes, insertion guidance and tunable parameters on real projects before enabling approved edits with isolated testing and rollback. Compare specialized models only after adequate eligible evidence exists.
7. Integrate ATLAS with the separate PLATZ Engine through authorized, versioned project interfaces when each product works independently and the engine's own directive defines its contract.
